# Memphisreo — технічна архітектура

*Статус: чернетка v0.2, оновлено 2026-10-05 (ADR-001). Перша версія — 2026-08-15. Доповнює [business-plan.md](business-plan.md).*

## 1. Принцип

Модульний моноліт (Spring Boot) + PostgreSQL, з мультитенантністю та
регіональним масштабуванням, закладеними в архітектуру з дня 1 так, щоб
не переписувати їх пізніше. Мікросервіси — не заборонені назавжди, а
відкладені до моменту, коли конкретна причина (не абстрактна) їх виправдає
(розділ 5).

## 2. Межі модулів (compute plane)

Один деплоюваний артефакт, Java-пакети за bounded context, без прямих
звернень між схемами модулів — тільки через публічний Java API модуля:

- `common` — спільна інфраструктура: `TenantContext`, базові виключення,
  JPA-конфігурація для tenant-routing. Не bounded context сам по собі,
  а плумбінг, яким користуються решта модулів.
- `security` — автентифікація (JWT, 2FA), `AccountIdentity`,
  `PlatformStaff`, RBAC (`Role`/`RolePermission`/`AgentRole`). Деталі —
  [security.md](security.md).
- `tenant` — реєстрація агенції, підписка, білінг-статус
- `agent` — профіль агента, запрошення (ролі/дозволи — в модулі `security`)
- `property` — об'єкти нерухомості
- `listing` — комерційна обгортка над property (ціна, статус, історія)
- `inquiry` — вхідні заявки з публічної сторінки лістингу (Фаза 1
  мінімальний сигнал, Фаза 2 — джерело конверсії в лід)
- `crm` (з фази 2) — `Client`, `Lead`, `LeadActivity`. Деталі —
  [domain-model.md §5](domain-model.md)
- `search` — індексація й пошук (кандидат на власну БД-репліку/Elasticsearch
  пізніше, вже зараз ізольований модуль)
- `media` — фото/відео/тури
- `deal` (Фаза 1) — `Showing`, `Offer`, `Deal` + чекліст угоди
  (domain-model.md §6)
- `rental` (пізніше, підключуваний) — договір оренди, орендар, графік
  платежів, акти. Ядро (`property`, `listing`) про оренду нічого не знає.

**Підключувані модулі.** Модуль, що вмикається не для всіх агенцій
(напр. `rental`), — це Maven-модуль зі своїми сутностями, сервісами й
міграціями, плюс запис у control plane `tenant_module (tenant_id,
module_code, enabled_at)`. Бекенд перевіряє ввімкненість на ендпоїнтах
модуля, фронт за тим самим списком показує/ховає розділи меню. Ядро
надає точки розширення (інтерфейси), а модуль їх реалізує — не навпаки.
Межі модулів перевіряються тестом (ArchUnit або Spring Modulith).

Виділення будь-якого з цих модулів в окремий сервіс — рефакторинг меж
деплойменту, не переписування бізнес-логіки, якщо межі модулів дотримані
з самого початку.

## 3. Мультитенантність (data plane) — ключове рішення

**Рішення: shared schema + `tenant_id` + PostgreSQL Row-Level Security +
cells.** Повне обґрунтування, розглянуті варіанти й наслідки —
[ADR-001](adr/001-shared-schema-rls-cells.md). Попереднє рішення
(schema-per-tenant) замінено 2026-10-05 з огляду на ціль у тисячі
агенцій.

Коротко:
- **Control plane** — спільна невелика схема: реєстр tenant-ів (id,
  назва, країна, статус, `cell`), облікові записи, конфігурація країн.
- **Data plane** — одна схема в межах комірки (cell); кожна
  tenant-scoped таблиця має `tenant_id`.
- **Ізоляція у чотири рубежі:** Hibernate `@TenantId` (застосунок) → RLS
  з `FORCE` і `SET LOCAL app.tenant_id` на кожну транзакцію (БД) →
  складені ключі `(tenant_id, id)` і складені FK (цілісність) → тести-
  інваріанти в CI.
- **Резолюція tenant-а** — лише з підписаного JWT claim `tenant_id`,
  кладеться в `TenantContext` (security.md §8).
- **Провіжинінг нового tenant-а** — рядок у control plane + засів
  вбудованих ролів; без створення схем і без прогону міграцій.
- **Міграції** — одна послідовність Flyway на комірку.

## 4. Регіональне масштабування

Регіональний розподіл — це маршрутизація запитів і розташування даних, не
поділ на сервіси:

1. Кожен регіон (напр. EU, UA) має одну або кілька комірок (cells) —
   окремих PostgreSQL-кластерів з даними tenant-ів цього регіону
   (ADR-001).
2. Той самий артефакт модульного моноліта деплоїться в кожному регіоні як
   горизонтально масштабована група однакових інстансів (autoscaling
   group / k8s Deployment), за балансувальником навантаження.
3. Маршрутизація запиту до регіону — на рівні edge (DNS/API gateway) за
   tenant → регіон з control plane, **до** того, як запит долетить до
   інстансу застосунку. Це уникає крос-регіональної латентності — інстанс
   у регіоні обробляє тільки tenant-ів свого регіону.
4. Умова, без якої це не працює: інстанси **stateless** — сесія в JWT, не
   в пам'яті процесу; файли в об'єктному сховищі (S3-сумісному), не на
   локальному диску інстансу.

Це паттерн, відомий у SaaS-архітектурі як "cell-based"/"pod" — кожен
регіон є незалежною коміркою з власними даними й обчисленнями, що
масштабується незалежно від інших регіонів. Не вимагає мікросервісів.

## 5. Коли реально знадобляться мікросервіси

Не "якщо", а конкретні тригери, щоб рішення приймалось по факту, а не
наперед:

- Модуль з принципово іншим профілем навантаження, що заважає іншим
  (напр. `media`-обробка CPU-важка і потребує масштабування окремо від
  CRUD API).
- Компонент з іншими вимогами до доступності/циклу релізів (напр.
  `billing`, де хочеться окремий, повільніший release cadence і суворіший
  контроль деплоїв).
- Окрема команда розробників, якій моноліт-репозиторій реально заважає
  (merge-конфлікти, конкуруючі релізи) — організаційна причина, не суто
  технічна.

До появи цих тригерів модульний моноліт із дотриманими межами модулів
(розділ 2) не є tech debt — він є проміжним, а не тимчасовим станом:
рефакторинг у сервіс, коли знадобиться, зачіпає межі деплойменту, а не
доменну логіку.

## 6. Вибір СУБД: PostgreSQL, не MySQL

Розглядалось через зручність MySQL Workbench для розробника. Рішення —
**PostgreSQL**, з причин, специфічних для домену нерухомості, не загальних
переваг:

- **PostGIS** — гео-пошук (радіус, намальований на мапі полігон, межі
  району) є core-фічею пошуку нерухомості з Фази 1, не майбутньою
  фічею. PostGIS — зрілий індустріальний стандарт; spatial-підтримка
  MySQL суттєво біднiша.
- **JSONB** — гнучкі per-country поля об'єкта нерухомості (розділ 4
  business-plan.md) природно лягають на індексований JSONB; MySQL JSON
  індексується гірше.
- **Row-Level Security** — додатковий рубіж ізоляції тенантів на рівні
  самої БД (politика "connection бачить тільки свій tenant_id" навіть
  якщо код помилково забув фільтр). Нативно відсутнє в MySQL.
- Ліцензія/governance — permissive license, community-governed, без
  залежності від комерційної політики одного вендора (Oracle).

Інструментарій для розробки не є блокером: **DBeaver** (безкоштовний,
кросбазовий) або **pgAdmin** як заміна MySQL Workbench; **IntelliJ
IDEA Ultimate** має вбудований DB-клієнт з повною підтримкою Postgres.

## 7. Object storage — рішення: MinIO (S3-сумісний)

Self-host для дев/раннього прод, той самий S3 API, що й AWS S3 — переїзд
на реальний S3 пізніше є заміною ендпоїнта, не переписуванням коду:
клієнт (`software.amazon.awssdk:s3`) працює з обома однаково. Код проти
власного інтерфейсу `ObjectStorage`, не напряму проти AWS SDK — друга
лінія захисту від прив'язки до конкретного провайдера. Використовується
модулем `document` (розділ 9) і пізніше — `media`.

## 8. Пошук — крос-тенантний денормалізований індекс

**Статус після ADR-001:** публічний портал відкладено (спочатку SaaS для
агенцій), тож цей індекс — заділ на майбутнє, не частина Фази 1.
Навігація й пошук **всередині агенції** йдуть напряму по основних
таблицях (індекси, що починаються з `tenant_id`), без цього індексу.

**Проблема, яку розв'язує цей розділ:** публічний пошук "по всіх
агенціях одразу" ("квартири в Києві до $100k") мусить бачити дані
різних tenant-ів і різних комірок (cells), тоді як основні таблиці
закриті RLS і розкидані по кластерах. Це очікуваний наслідок сильної
ізоляції, і
його розв'язують так само всі маркетплейси (Zillow, Airbnb): окремий
**денормалізований пошуковий індекс**, куди кожен tenant пише при
публікації, а публічний пошук читає з нього, не з tenant-схем.

**Рішення для Фази 3: PostgreSQL, не Elasticsearch — поки що.** Той
самий принцип, що і з мікросервісами (розділ 5): не тягнути додаткову
інфраструктуру (окремий сервіс, синхронізація, моніторинг) без
конкретної причини масштабу. PostgreSQL з правильними індексами
(B-tree на структуровані поля, GiST на geo через PostGIS, GIN на JSONB
і tsvector на full-text) комфортно тримає мільйони рядків для такого
патерну фільтрації — переїзд на Elasticsearch/OpenSearch, коли
конкретний обсяг чи вимоги до faceted search це виправдають, це заміна
реалізації за інтерфейсом `SearchIndexer` (нижче), не переписування
системи.

**Схема:** окрема, НЕ tenant-scoped схема `search` (без RLS), запис —
через роль `memphisreo_platform` (ADR-001). Одна таблиця
`search.listing_search_document` — по одному денормалізованому рядку
на кожен `Listing`, з `tenant_id` як звичайною колонкою (не межею
ізоляції — тут навпаки, весь сенс у крос-tenant видимості).

**Синхронізація — явний виклик з композиційного кореня, не тригер БД
чи message queue.** Той самий принцип "explicit over magic", що й
скрізь у проєкті (ручний `TenantContext`, явний
`TenantProvisioningService`). `ListingSearchDocument` денормалізує
поля не тільки з `Listing`, а і з `Property`/`Address` (інший модуль)
— тому сам `ListingService` (module boundary: тільки сирі UUID, без
JPA-звʼязків між модулями) цей виклик зробити не може. Синхронізацію
робить `ListingController` у `platform-app` — після
`listingService.create()` явно підвантажує `Property`+`Address` і
викликає `SearchIndexer.index(...)`, той самий композиційно-кореневий
патерн, що й `TenantRegistrationService`/`AgentInvitationService`.
Interface `SearchIndexer` — контракт, що не залежить від того,
Postgres за ним чи Elasticsearch:

```java
public interface SearchIndexer {
    void index(ListingSearchDocument document);
    void remove(UUID listingId);
}
```

**Наслідок для мультитенантності:** записи в `search`-схему йдуть з
tenant-scoped виклику (`ListingService`, що працює під поточним
`TenantContext` агенції), у СПІЛЬНУ схему — сутність `ListingSearchDocument`
прибита до `schema = "search"` явно (`@Table`) і пишеться окремим
`DataSource` з роллю, що має `BYPASSRLS`.

**Відкрито:** сам публічний query-ендпоїнт (фільтри, пагінація,
сортування, facets) — не спроєктовано в цьому розділі, це окрема
задача поверх уже закладеної схеми й механізму синхронізації. Також
відкрито: чи потрібен окремий крок ресинхронізації при редагуванні
`Property` (зараз синхронізація прив'язана лише до `ListingService`).

## 9. Відкриті технічні питання

- Query-ендпоїнт публічного пошуку (розділ 8) — фільтри/пагінація/facets.
- Конкретні регіони деплою (які саме дата-центри для EU vs UA-адʼязного
  трафіку) — інфраструктурне рішення поза межами цього документа.
