# ADR-001: Мультитенантність — shared schema + RLS + cells

*Статус: прийнято, 2026-10-05. Замінює попереднє рішення "schema-per-tenant"
(architecture.md §3 до цієї дати).*

## Контекст

Ціль — тисячі й більше агенцій (tenant-ів) по Україні та ЄС. Вимога —
сильна ізоляція даних агенцій з дня 1. Перша реалізація використовувала
окрему PostgreSQL-схему на кожного tenant-а. Живих даних ще немає, тож
змінити модель зараз дешево.

## Розглянуті варіанти

1. **Schema-per-tenant** (поточна реалізація).
2. **Shared schema + `tenant_id`** без додаткових механізмів.
3. **Shared schema + `tenant_id` + Row-Level Security + cells** (обрано).
4. **Database-per-tenant**.

## Рішення

Варіант 3. Усі агенції однієї комірки (cell) — в одних і тих самих
таблицях, розрізнені колонкою `tenant_id`. Ізоляція забезпечується кількома
незалежними рубежами, жоден з яких не покладається на уважність розробника.

### Рубіж 1 — застосунок (Hibernate)

Дискримінаторна мультитенантність Hibernate 6 (`@TenantId` на полі
`tenantId` сутності + `CurrentTenantIdentifierResolver` з `TenantContext`).
Hibernate сам додає фільтр за tenant до кожного запиту й сам проставляє
`tenant_id` при вставці.

### Рубіж 2 — база даних (RLS)

```sql
ALTER TABLE property ENABLE ROW LEVEL SECURITY;
ALTER TABLE property FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON property
    USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
    WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

- На початку кожної транзакції: `SET LOCAL app.tenant_id = '<tenant з JWT>'`.
  `SET LOCAL` живе лише в межах транзакції — сумісно з пулом з'єднань і
  PgBouncer у transaction mode; значення не "протікає" в наступний запит.
- Без встановленого `app.tenant_id` політика не пропускає жодного рядка
  (fail closed).
- **Ролі БД:** `memphisreo_owner` (власник таблиць, міграції Flyway),
  `memphisreo_app` (застосунок; не власник, без `BYPASSRLS`),
  `memphisreo_platform` (з `BYPASSRLS` — лише platform admin, пошуковий
  індекс, фонові job-и; окремий `DataSource`, використання явне).

### Рубіж 3 — цілісність посилань

Первинні ключі tenant-scoped таблиць — `(tenant_id, id)`, зовнішні —
складені: `FOREIGN KEY (tenant_id, property_id) REFERENCES property (tenant_id, id)`.
БД фізично не дасть прив'язати запис агенції A до запису агенції B —
цю дірку RLS сам не закриває (RLS фільтрує читання, а не FK-перевірки).

### Рубіж 4 — тести в CI

- Тест-інваріант: кожна таблиця з колонкою `tenant_id` має RLS-політику
  і `FORCE ROW LEVEL SECURITY` (перевірка через `pg_class`/`pg_policies`).
  Нова таблиця без політики ламає збірку.
- IT ізоляції: дві агенції, кожен ендпоїнт перевіряється на відсутність
  перехресного доступу (читання, зміна, посилання на чужий id).

### Продуктивність

Індекси tenant-scoped таблиць починаються з `tenant_id`
(`(tenant_id, status, updated_at)` тощо) — запит агенції читає лише її
рядки незалежно від кількості сусідів. Великі таблиці (медіа, активності,
аудит) за потреби — hash-партиціювання за `tenant_id` без змін у коді.

### Cells (комірки)

Control plane тримає мапу `tenant → cell`. Cell — окремий PostgreSQL-кластер
(орієнтовно 1–3 тис. агенцій) з ідентичною схемою й тим самим артефактом
застосунку. Нова комірка відкривається, коли поточна заповнюється.

- **Data residency:** UA-агенції — в UA-комірці, ЄС — в EU-комірці.
- **Радіус аварії:** падіння однієї комірки не зачіпає інших.
- **Міграції:** N прогонів = кількість комірок (одиниці), не tenant-ів;
  можливий поступовий rollout комірка за коміркою.
- **Escape hatch:** велика агенція або контрактна вимога виділеної
  інфраструктури — власна комірка з одним tenant-ом. Код той самий.

На старті — одна комірка. Маршрутизація між комірками — на рівні edge
(див. architecture.md §4), застосунок в комірці обслуговує лише своїх tenant-ів.

## Чому не інші варіанти

**Schema-per-tenant** — добре працює на десятках/сотнях tenant-ів, на
тисячах проблеми ростуть лінійно:
- міграції = N прогонів Flyway (5000 × ~0,5 с ≈ 40 хв), часткове
  застосування лишає агенції на різних версіях схеми;
- каталог Postgres: тисячі схем × десятки таблиць × індекси = сотні
  тисяч relations; relcache кожного з'єднання росте, `pg_dump`/autovacuum
  деградують;
- перемикання `search_path` у спільному пулі — крихке, забутий reset =
  витік між tenant-ами;
- крос-тенантні задачі (адмінка, аналітика, білінг, пошук) потребують
  обхідних рішень;
- noisy neighbor не вирішує — схеми ділять один фізичний сервер.

**Shared schema без RLS** — один пропущений фільтр = витік даних; вимога
сильної ізоляції не виконана.

**Database-per-tenant** — найсильніша ізоляція, але тисячі БД — це
тисячі пулів з'єднань і операційна вартість, невиправдана для малих
агенцій. Лишається доступною як "cell з одним tenant-ом".

## Наслідки

**Що втрачаємо і як компенсуємо:**
- Видалення tenant-а (GDPR) — не `DROP SCHEMA`, а фоновий job:
  `DELETE ... WHERE tenant_id = ?` по всіх таблицях + видалення префікса
  `tenants/<tenant_id>/` в об'єктному сховищі, з затримкою-підтвердженням.
- Експорт/бекап однієї агенції — логічний експорт за `tenant_id`; повний
  бекап — на рівні комірки. Відновлення однієї агенції — з бекапу комірки
  в тимчасову БД з перенесенням її рядків (рідкісна операція).

**Зміни в коді (крок 0 плану):**
- Прибрати: `SchemaMultiTenantConnectionProvider`, `TenantSchemaResolver`,
  `JpaTenantSchemaResolver`, створення схем у `TenantProvisioningService`,
  `TenantMaintenanceRunner` (його функцію донарахування permission-ів
  вбудованим ролям перенести в одноразову міграцію/job).
- Прибрати `tenant.schema_name`; додати `tenant.cell`.
- Додати: `@TenantId`, встановлення `app.tenant_id` на початку транзакції,
  ролі БД, RLS-політики й складені ключі в міграціях, тести з рубежу 4.
- Міграції tenant-baseline переносяться в одну послідовність Flyway
  (одна схема `app`). Оскільки прод-даних немає, baseline перезбирається
  один раз; після першого прод-деплою — лише нові міграції.
